# /daily — unattended orchestrator

The cornerstone workflow. Runs unattended via launchd at 07:00 local time, also invokable on demand. Pulls the user's overnight Sheet decisions, reconciles the manual queue, imports the jobs the user saved on SEEK, hunts fresh roles across enabled channels, drafts application packages and outreach, submits SEEK Quick Apply and LinkedIn Easy Apply applications on autopilot, mirrors everything back to the Sheet, and writes a journal digest.

**Autopilot contract (user decision 2026-09-15; LinkedIn added 2026-09-16).** This run may submit SEEK Quick Apply and LinkedIn Easy Apply applications (channels listed in `autopilot.channels`) without a human reading the package first. Authority comes from the machine gates, not from this skill: `tools/autopilot-submit.ts` runs `tools/letter-critic.ts` on the exact letter and then `tools/submission-gate.ts` with `--approved-by autopilot:<run-id>`; the gate requires `autopilot.enabled` in `state/profile/submission-policy.yaml`, status `approved`, agent classification, core discipline or a user-saved row, no `red_flag_blocker`, a letter-critic pass whose sha matches the letter, the kill switch off and `autopilot.max_per_day` not reached. Never call `npm run submit:seek` or `npm run submit:linkedin` directly from this skill; always go through `npm run autopilot:submit`, which dispatches to the channel adapter. LinkedIn "Apply on company website" ads (`applyMethod` other than `easy_apply`), every other portal, and every recruiter or hiring-manager message remain attended or draft-only.

## Sequence

Resolve the repo root first: run `bash .claude/hooks/repo-root.sh` and treat its output as the base for every path below; never assume cwd. Prefix every npm call with `TMPDIR=/tmp` (sandbox). Use `RUN_ID=daily-<YYYY-MM-DD>` for the whole run.

1. **Pull Sheet decisions** — invoke `state-syncer` with `--pull-first`. That runs `npm run sheets:pull`, reading the Tray's `Action` + `Edits` columns into `state/pipeline/approval-queue.json` and clearing those cells.
2. **Reconcile decisions** — process `reject`, `hold`, and `edit` actions through the pipeline's normal state transitions. A Sheet `approve` on a SEEK or LinkedIn Easy Apply row means: finish and validate the package, then let step 4b submit it. A Sheet `approve` on any other channel prepares the package into `manual_action_needed` for an attended session. Leave edits for re-assembly in step 4.
3. **Hunt** — invoke `opportunity-finder` with all enabled channels. It dedups against the pipeline, classifies through the agent, scores deterministically, and ingests new opportunities as `discovered`, `shortlisted` or `parked`.

   **3a. Saved SEEK jobs (before the hunt).** Run `TMPDIR=/tmp npm run -s seek:saved -- --upsert`. Every job the user saved on SEEK is upserted with `userSaved: true` / `userSavedAt`. A saved job is an order to apply, no questions (user, 2026-09-15): classify it like any other row (agent classification, full JD via `seek:enrich` if the card is a blurb; if the classifier returns no positioning, assign the closest one), then always draft and submit it. Nothing parks a saved row: not the discipline band, score, location, duplicate status, employment type or clearance wording. The letter names any gap honestly and the letter-critic still applies; the gate bypasses `red_flag_blocker` for user-saved rows. **Saved rows are never left stranded (user, 2026-09-17):** the retry set for this step is every `userSaved: true` SEEK row that is still on the live saved list and is not `submitted`, whatever its status. A saved row sitting in `manual_action_needed` from an earlier critic block is re-drafted this run; a saved row in `rejected` as a duplicate is reopened (`set-status discovered`, reason "user saved after rejection") and drafted, because a saved job overrides duplicate status. Only a non-Quick-Apply ad (external ATS) or an unknown screening question is a legitimate reason for a saved row to stay in `manual_action_needed`, and the note must say which.

4. **Draft** — for each opportunity newly in `shortlisted`, each saved row from 3a, and each opportunity flagged for `edit` in step 2, run the **application-assembly orchestration** — the same pattern as `/apply`: spawn `cover-letter-writer` (and `resume-writer` if the opportunity needs JD-tailoring) as peer subagents in one message. For each new LinkedIn hiring post, invoke `outreach-drafter`. All drafts route through the slop-killer + voice-check + lint pipeline before the opportunity moves to `awaiting_approval`. Package the archive as `/apply` does: `state/pipeline/archive/<id>/{jd.md, cover-letter.md, metadata.json, <resume>.docx/.pdf}`; `metadata.json` must name the resume docx (`resume.docx`) so autopilot picks the right stored resumé on SEEK or uploads that exact file on LinkedIn (Easy Apply has no cover-letter field on most ads; the letter still gates and is journaled, but the employer sees the CV and profile).

   **Read the letter once yourself before it goes further.** The orchestrator's re-read has caught venture work attributed to the lender, an unsupported "stayed on schedule", the 12.9 TB file-share estate called a SharePoint estate, and a recruiter named as the client. Fix corpus-traceable facts only; never add a claim.

   **A positioning with no keyword cloud is never rendered.** Market narrative comes first, and an unattended run cannot do the research interview. Before spawning `resume-writer` for a JD-tailored CV, run `npm run resume:context -- --resume <resume-id>` and read the `clouds` block. If `clouds.missing` is true, skip the render for that opportunity: leave it without a tailored CV, journal it by name, and queue the `/resume-strategy` cloud refresh (steps 3b + 3c) for the next attended session. A `clouds.stale` positioning may still render, but the journal must name the stale cloud for refresh. Never mine, invent or half-build a cloud unattended — the qualification interview needs the user.

   **Keyword questions are queued, never asked.** Before spawning the writers for an opportunity, run `npm run resume:keywords -- --resume <resume-id> --jd <archive>/jd.md --opportunity <opportunity-id>`, then `npm run resume:keyword-confirm -- queue --plan <archive>/keyword-plan.json --origin daily`. That records every plan question as `pending, origin: daily` without asking and never reopens a row the user already answered. Render **without** those terms — a pending row authorises nothing. Write the plan's `renderable_pct` / `surfaced_pct` and the pending count into `archive/<opportunity-id>/metadata.json`, and add a tray note when must-have renderable coverage is below 60%. `/review-drafts` and `/resume-review` drain the queue when the user is next at the laptop.

   **4b. Autopilot submit.** For each package whose letter passed slop and voice (new packages from this run, saved rows, and any SEEK or LinkedIn row already at `awaiting_approval` / `approved` with a package and no send), run:

   ```
   TMPDIR=/tmp npm run -s autopilot:submit -- --id <opportunity-id> --run-id $RUN_ID
   ```

   The tool runs the letter-critic (reusing a current pass), walks the status to `approved`, runs the gate with autopilot provenance, calls the channel adapter (SEEK Quick Apply or LinkedIn Easy Apply), and on a confirmed success page moves the row to `submitted`, writes `confirmation.txt`, logs an audit event with actor `autopilot`, and unsaves the job on SEEK if the user had saved it. Record each outcome from the printed JSON (`outcome`, `reason`, `gate.action`, `critic`). Exit 0 is a send; anything else is parked: letter-critic block, gate `gate_failed` / `manual` / `duplicate`, external-ATS redirect, unknown screening question, adapter failure all land in `manual_action_needed` with the reason in `notes` for the Tray. **Exception, critic block on a user-saved row (user, 2026-09-17):** hand the critic's findings back to `cover-letter-writer` for a regeneration (the writer fixes the named sentences against the corpus; it does not soften the disclosed gap), re-run `autopilot:submit`, and allow up to two regenerations per row per run before parking with the final findings in `notes`. This is the one case where a letter is rewritten to satisfy the critic unattended; non-saved rows keep the park-and-read rule. Gate `blocked` (kill switch) or `capped` leaves the row at `approved` for a later run; stop submitting for the day on either. Never retry a send in the same run; never touch the browser yourself to finish one.

5. **Mirror & journal** — invoke `state-syncer` (no `--pull-first` this time). It pushes Pipeline + Tray + Followups tabs and regenerates `state/pipeline/opportunities.md`. Then write the day's `state/journal/YYYY-MM-DD.md` digest (counts, top 5 finds, saved-job imports, anything that needed manual attention). Under a **"Sent unattended"** heading, list every autopilot send with role, advertiser, SEEK job id, resume filename, confirmation text, letter-critic warn count, and the **full cover-letter text** so the user can audit each morning. Under "Parked by autopilot", list every row that did not send with its reason. Include two keyword-loop lines: the count of pending `kind: keyword` rows in `state/profile/market-confirmations.yaml` (person-wide; an answer applies to every positioning; add a tray note when more than 10 are pending), and a reminder to run the `/resume-strategy` cloud refresh for any active type that references no clouds or whose load-bearing clouds (weight >= 4) are older than 30 days, naming every positioning whose renders this run skipped for a missing cloud (`npm run resume-types:validate` warns on this).

6. **Daily summary** — run `TMPDIR=/tmp npm run -s daily:summary -- --notify`. It writes `state/journal/summary/<date>.md` (sent today with actor and confirmation, escalations with the exact next action, queue and parked movement, responses, a numbers table), refreshes the Sheet `Summary` tab and posts a macOS notification with the one-line headline. Run it last so it sees the mirrored state and the journal; it never mutates the pipeline, and it degrades to a stderr note when the Sheet is not configured. `--date YYYY-MM-DD` re-summarises an earlier day; `--json` prints the structured object.

## Failure handling (headless mode)

When invoked headlessly (launchd), the daily run cannot ask questions. So at decision forks, take the safe default and log the decision in the journal for the user to review:

- Channel login expired → skip that channel, log it. If the SEEK session is expired, `seek:saved` and `autopilot:submit` both fail closed; if the LinkedIn session is expired, `hunt:linkedin-jobs` returns nothing and `autopilot:submit` parks LinkedIn rows with "signed out"; journal it (`npm run login:linkedin` / `login:seek` for the user) and leave packages at `awaiting_approval`.
- Letter-critic block → the row goes to `manual_action_needed` with the findings in `<archive>/letter-critic.json`. Do not rewrite the letter to satisfy the critic in the same run; the user reads the findings first.
- Gate `gate_failed` / `manual` / `duplicate` → manual queue with the gate reason. Gate `blocked` or `capped` → stop submitting, leave the rest at `approved`, journal it.
- External ATS redirect (applr.io, JobAdder, SuccessFactors, employer portal) → manual queue; write `manual-checklist.md` if the adapter did not.
- Unknown screening question → the adapter stops before Continue; the question lands in `state/profile/screening-answers.yaml` `unknown_questions:` and the row in `manual_action_needed`. Never invent an answer.
- Keyword questions from `resume:keywords` → queue them as `pending` via `keyword-confirm queue --origin daily`, render without them, and note the count in the journal. Never ask, never confirm, never patch `cv-source.md` from an unattended run.
- No keyword clouds (`clouds.missing`) → do not render that positioning. Journal the positioning and the opportunities it blocked, and queue the cloud refresh for the next attended session.
- Slop-killer fails after 4 regens → leave the role in `drafted` (not `awaiting_approval`), note the persistent hit in the journal for the user to break the tie. It is not submitted.
- Saved row with an existing-clearance or fixed-term/permanent requirement → park with the reason; do not draft.
- Sheet auth missing → skip Sheet sync (the rest still works).

When invoked interactively, the same defaults apply but surface a short summary at the end inviting the user to inspect anything that needed a fallback.

## Boundaries

- SEEK Quick Apply and LinkedIn Easy Apply are the only unattended submission paths, and only through `npm run autopilot:submit` (which owns the letter-critic, the gate and the audit trail). Never call `npm run submit:seek`, `npm run submit:linkedin`, a browser tool, or any other adapter from this workflow.
- LinkedIn Easy Apply, every other portal and every external ATS stay attended: prepare the package into `manual_action_needed`.
- Recruiter and hiring-manager email is always a Gmail draft, never sent. LinkedIn comments and DMs stay in the tray.
- A user-saved SEEK job is an order to apply; a Sheet `approve` on any other channel is preparation only.
- The kill switch (`kill_switch: true`) and `autopilot.enabled: false` each halt every autopilot send; treat the daily caps, validation gates, channel policy and dedup as further safeguards, never as extra authority.
- Don't crash the run on one channel's or one row's failure; isolate and report.
