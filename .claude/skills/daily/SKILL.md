# /daily: unattended orchestrator

The cornerstone workflow. Runs unattended via launchd at 07:00 local time, also invokable on demand. Pulls the user's overnight Sheet decisions, reconciles the manual queue, imports the jobs the user saved on SEEK, hunts fresh roles across enabled channels, drafts application packages and outreach, submits SEEK Quick Apply and LinkedIn Easy Apply applications on autopilot, mirrors everything back to the Sheet, and writes a journal digest.

**Autopilot contract (user decision 2026-09-15; LinkedIn added 2026-09-16).** This run may submit SEEK Quick Apply and LinkedIn Easy Apply applications (the channels listed in `autopilot.channels`) without a human reading the package first. Authority comes from the machine gates, not from this skill: see `AGENTS.md` section 2 and `references/harness/autopilot-gates.md` for the gate list. Never call `npm run submit:seek` or `npm run submit:linkedin` directly from this skill; always go through `npm run autopilot:submit`, which dispatches to the channel adapter. LinkedIn "Apply on company website" ads (`applyMethod` other than `easy_apply`), every other portal, and every recruiter or hiring-manager message remain attended or draft-only.

## Sequence

Resolve the repo root first (`references/harness/repo-root.md`). Prefix every npm call with `TMPDIR=/tmp` (sandbox). Use `RUN_ID=daily-<YYYY-MM-DD>` for the whole run.

When `scripts/daily.sh` invokes this skill, the deterministic front half has already run and its compact report is at `state/journal/front-half/<date>.json`. Read that report and do not repeat Sheet pull, saved-job import, channel hunts, Jev classification, scoring or deterministic dedup. When the skill is invoked directly, run `TMPDIR=/tmp npm run -s daily:front-half` first. The front half does not depend on Claude Code or Codex and remains available when either CLI is unavailable.

1. **Pull Sheet decisions**: this is owned by `daily:front-half`. It runs `sheets:pull` when the Sheet is enabled and records the result in the front-half report. Do not invoke a second pull from the agentic back half. When the Sheet is off, the local UI has already written its decisions straight into the pipeline and the step reports `skipped: "sheet.enabled=false"`.
2. **Reconcile decisions**: process `reject`, `hold`, and `edit` actions through the pipeline's normal state transitions, from the approval queue and from any row the local UI already moved. An `approve` on a SEEK or LinkedIn Easy Apply row means: finish and validate the package, then let step 4b submit it. A Sheet `approve` on any other channel prepares the package into `manual_action_needed` for an attended session. Leave edits for re-assembly in step 4.
   Run `TMPDIR=/tmp npm run -s screening:retry-queue` and process its `attended_preparation` separately from retry candidates. These external-portal rows lack a current passing letter verdict. First verify the advert is open and employment terms satisfy the profile, preserving saved-job exceptions. Fixed-term employee roles are not ABN contracts merely because the channel labels them Contract. Close confirmed ineligible or expired unsaved roles through the normal audited transitions; leave genuinely unknown terms for research, not an invented answer. For eligible rows, prepare or repair through `cover-letter-writer` and re-run the package gates. Never send these portal rows unattended. Only a current passing package returns to the person's portal queue.
3. **Hunt, expire and classify**: this is owned by `daily:front-half`. Enabled channel adapters ingest with `--upsert`; explicit closing dates and channel-expired adverts are closed before any model call; deterministic extraction records explicit facts; Jev makes the bounded semantic decisions; and the deterministic scorer places automatic decisions into `discovered`, `shortlisted` or `parked`. Do not classify the batch in-agent. If the front-half report says Jev degraded, leave affected rows unpromoted, record the degradation, and continue only with already classified work. Autopilot remains blocked until the degradation is healthy or explicitly acknowledged.

   The generic-agent ClassificationV2 path is bounded verification, not the batch default. Run `npm run -s jev:verification-queue` and review only the rows it returns: ordinary Jev-positive unattended candidates, saved jobs, and the small high-scoring adjacent/platform-gap parachute. The parachute exists because the corrected core-only metric found one historically submitted role that Jev would otherwise have dropped; it never expands to all Jev rejections. The agent must return the bounded semantic fields as JSON, then persist them through `npm run -s jev:agent-fallback -- --id <opportunity-id> --model <model-id> --json '<decision-json>'`. For a saved outside-discipline job, keep `discipline_fit: outside` and choose the closest honest active resume as packaging in `matched_resume_id`. After adopting decisions, rescore those ids so a verified core row can enter the queue. This supersedes the Jev decision with source `agent_fallback`. Only that automatic verification can satisfy the unattended classification prerequisite, and it never bypasses any other autopilot gate. Do not write an improvised classification directly into the pipeline or classify the whole batch in-agent.

   Then clear the tail of the discovery backlog: `TMPDIR=/tmp npm run -s pipeline:flush-discovered -- --older-than 14d --unclassified --apply`.

   **3a. Saved SEEK jobs (before the hunt).** The front half runs `seek:saved -- --upsert`. Every job the user saved on SEEK is upserted with `userSaved: true` / `userSavedAt`. A saved job is an order to apply: follow `references/harness/saved-jobs-rule.md` in full (classify, always draft, always retry every saved row that is not `submitted`, reopen a saved row rejected as a duplicate, up to two critic regenerations, park only for an external ATS or an unknown screening question and say which).

4. **Draft**: for each opportunity newly in `shortlisted`, each saved row from 3a, and each opportunity flagged for `edit` in step 2, run the **application-assembly orchestration**, the same pattern as `/apply`: spawn `cover-letter-writer` (and `resume-writer` if the opportunity needs JD-tailoring) as peer subagents in one message. For each new LinkedIn hiring post, invoke `outreach-drafter`. All drafts route through the slop-killer + voice-check + lint pipeline before the opportunity moves to `awaiting_approval`. Package the archive as `/apply` does: `state/pipeline/archive/<id>/{jd.md, cover-letter.md, metadata.json, <resume>.docx/.pdf}`; `metadata.json` must name the resume docx (`resume.docx`) so autopilot picks the right stored resumé on SEEK or uploads that exact file on LinkedIn (Easy Apply has no cover-letter field on most ads; the letter still gates and is journaled, but the employer sees the CV and profile).

   **Read the letter once yourself before it goes further.** The orchestrator's re-read has caught venture work attributed to the lender, an unsupported "stayed on schedule", the 12.9 TB file-share estate called a SharePoint estate, and a recruiter named as the client. Fix corpus-traceable facts only; never add a claim.

   **A positioning with no keyword cloud is never rendered.** Market narrative comes first, and an unattended run cannot do the research interview. Before spawning `resume-writer` for a JD-tailored CV, run `npm run resume:context -- --resume <resume-id>` and read the `clouds` block. If `clouds.missing` is true, skip the render for that opportunity: leave it without a tailored CV, journal it by name, and queue the `/resume-strategy` cloud refresh (steps 3b + 3c) for the next attended session. A `clouds.stale` positioning may still render, but the journal must name the stale cloud for refresh. Never mine, invent or half-build a cloud unattended; the qualification interview needs the user.

   **Keyword questions are queued, never asked.** Before spawning the writers for an opportunity, run `npm run resume:keywords -- --resume <resume-id> --jd <archive>/jd.md --opportunity <opportunity-id>`, then `npm run resume:keyword-confirm -- queue --plan <archive>/keyword-plan.json --origin daily`. That records every plan question as `pending, origin: daily` without asking and never reopens a row the user already answered. Render **without** those terms: a pending row authorises nothing. Write the plan's `renderable_pct` / `surfaced_pct` and the pending count into `archive/<opportunity-id>/metadata.json`, and add a tray note when must-have renderable coverage is below 60%. Then, once every opportunity in this run has been queued, invoke the `keyword-triage` skill: it applies the deterministic rejects and answers from the corpus unattended (it never asks and never patches `cv-source.md`), so the queue the user meets is only genuine skill questions. `/review-drafts` and `/resume-review` drain what is left when the user is next at the laptop.

   **4b. Autopilot submit.** First run `TMPDIR=/tmp npm run -s screening:retry-queue`. This read-only queue finds manual rows whose exact current screening blocker now has a saved answer. Include these candidates even when they are not user-saved. Do not ask the person to answer again. Recheck advert expiry, classification and package readiness; prepare missing or stale artefacts through the normal writers. External portals are excluded and remain attended. Queue membership does not bypass any submission gate. For each package whose letter passed slop and voice (new packages from this run, saved rows, recovered screening candidates, and any SEEK or LinkedIn row already at `awaiting_approval` / `approved` with a package and no send), run:

   ```
   TMPDIR=/tmp npm run -s autopilot:submit -- --id <opportunity-id> --run-id $RUN_ID
   ```

   The tool runs the letter-critic (reusing a current pass), walks the status to `approved`, runs the gate with autopilot provenance, calls the channel adapter (SEEK Quick Apply or LinkedIn Easy Apply), and on a confirmed success page moves the row to `submitted`, writes `confirmation.txt`, logs an audit event with actor `autopilot`, and unsaves the job on SEEK if the user had saved it. Record each outcome from the printed JSON (`outcome`, `reason`, `gate.action`, `critic`). Exit 0 is a send; gate `gate_failed` / `manual` / `duplicate`, external-ATS redirect, unknown screening question and adapter failure land in `manual_action_needed` with the reason in `notes`. A letter-critic block is run-owned repair work, not a user decision: hand the findings back to `cover-letter-writer`, re-run `autopilot:submit`, and allow up to two regenerations per row per run. Clear `redraftRequested` as soon as a regeneration lands (`npm run pipeline -- patch --id <id> --json '{"redraftRequested": null}'`). If both regenerations fail, keep a user-saved row in `manual_action_needed`; move an unsaved row to `rejected` with the final findings in its history. Gate `blocked` (kill switch) or `capped` leaves the row at `approved` for a later run; stop submitting for the day on either. Never retry a send in the same run; never touch the browser yourself to finish one.

   **4c. Critic digest.** After the last `autopilot:submit` call, run:

   ```
   TMPDIR=/tmp npm run -s letter:critic -- --digest --since 14d
   ```

   It reads every `state/pipeline/archive/*/letter-critic.json` from the last fortnight and groups the `fail` findings of blocked verdicts into themes. No model call, no state change. Append its `themes` to today's journal under a **"Critic digest"** heading: one line per theme with `key`, `count`, the opportunity ids and the `proposed_rule` candidate. Every theme with `count >= 2` also goes into the daily summary's **"Observations for the user"** as a candidate for promotion into `state/profile/letter-critic-rules.yaml`. Promotion is an attended decision: never edit `letter-critic-rules.yaml`, `cv-source.md` or any profile file from this run. The digest reports, the user rules.

5. **Mirror & journal**: invoke `state-syncer` (no `--pull-first` this time). It regenerates `state/pipeline/opportunities.md` and, when `sheet.enabled` is true, pushes the Pipeline + Tray + Followups tabs; with the Sheet off it reports `sheet: disabled` and the local work still runs. Then write the day's `state/journal/YYYY-MM-DD.md` digest (counts, top 5 finds, saved-job imports, anything that needed manual attention). Under a **"Sent unattended"** heading, list every autopilot send with role, advertiser, SEEK job id, resume filename, confirmation text, letter-critic warn count, and the **full cover-letter text** so the user can audit each morning. Under "Parked by autopilot", list every row that did not send with its reason. Include two keyword-loop lines: the count of pending `kind: keyword` rows in `state/profile/market-confirmations.yaml` (person-wide; an answer applies to every positioning; add a tray note when more than 10 are pending), and a reminder to run the `/resume-strategy` cloud refresh for any active type that references no clouds or whose load-bearing clouds (weight >= 4) are older than 30 days, naming every positioning whose renders this run skipped for a missing cloud (`npm run resume-types:validate` warns on this).

6. **Daily summary**: run `TMPDIR=/tmp npm run -s daily:summary -- --notify`. It writes `state/journal/summary/<date>.md` (sent today with actor and confirmation, escalations with the exact next action, queue and parked movement, responses, a numbers table), refreshes the Sheet `Summary` tab when `sheet.enabled` is true, and posts a macOS notification with the one-line headline. Run it last so it sees the mirrored state and the journal; it never mutates the pipeline, and it degrades to a stderr note when the Sheet is not configured. `--date YYYY-MM-DD` re-summarises an earlier day; `--json` prints the structured object.

## Failure handling (headless mode)

When invoked headlessly (launchd), the daily run cannot ask questions. So at decision forks, take the safe default and log the decision in the journal for the user to review:

- Channel login expired → skip that channel, log it. If the SEEK session is expired, `seek:saved` and `autopilot:submit` both fail closed; if the LinkedIn session is expired, `hunt:linkedin-jobs` returns nothing and `autopilot:submit` parks LinkedIn rows with "signed out"; journal it (`npm run login:linkedin` / `login:seek` for the user) and leave packages at `awaiting_approval`.
- Letter-critic block → regenerate through `cover-letter-writer` with the findings, up to twice. After two failed repairs, keep a user-saved row for the person and close an unsaved row as rejected. The critic artefact remains in `<archive>/letter-critic.json` either way.
- Gate `gate_failed` / `manual` / `duplicate` → manual queue with the gate reason. Gate `blocked` or `capped` → stop submitting, leave the rest at `approved`, journal it.
- External ATS redirect (applr.io, JobAdder, SuccessFactors, employer portal) → manual queue; write `manual-checklist.md` if the adapter did not.
- Unknown screening question → the adapter stops before Continue; the question lands in `state/profile/screening-answers.yaml` `unknown_questions:` and the row in `manual_action_needed`. Never invent an answer.
- Keyword questions from `resume:keywords` → queue them as `pending` via `keyword-confirm queue --origin daily`, render without them, and note the count in the journal. Never ask, never confirm, never patch `cv-source.md` from an unattended run.
- No keyword clouds (`clouds.missing`) → do not render that positioning. Journal the positioning and the opportunities it blocked, and queue the cloud refresh for the next attended session.
- Slop-killer fails after 4 regens → leave the role in `drafted` (not `awaiting_approval`), note the persistent hit in the journal for the user to break the tie. It is not submitted.
- Saved row whose ad carries an existing-clearance, fixed-term or permanent requirement → still draft and submit it; the letter names the gap honestly and the gate bypasses `red_flag_blocker` for saved rows (`references/harness/saved-jobs-rule.md`). Only a non-Quick-Apply ad or an unknown screening question leaves a saved row unsent.
- Sheet auth missing, or `sheet.enabled: false` → skip the Sheet steps (the rest still works; a disabled Sheet is a choice, not a fault, and is not worth a journal line).

When invoked interactively, the same defaults apply but surface a short summary at the end inviting the user to inspect anything that needed a fallback.

## Boundaries

- SEEK Quick Apply and LinkedIn Easy Apply are the only unattended submission paths, and only through `npm run autopilot:submit` (which owns the letter-critic, the gate and the audit trail). Never call `npm run submit:seek`, `npm run submit:linkedin`, a browser tool, or any other adapter from this workflow.
- LinkedIn ads with any apply method other than `easy_apply`, every other portal and every external ATS are attended-only: prepare the package into `manual_action_needed`.
- Recruiter and hiring-manager email is always a Gmail draft, never sent. LinkedIn comments and DMs stay in the tray.
- A user-saved SEEK job is an order to apply; a Sheet `approve` on any other channel is preparation only.
- The kill switch (`kill_switch: true`) and `autopilot.enabled: false` each halt every autopilot send; treat the daily caps, validation gates, channel policy and dedup as further safeguards, never as extra authority.
- Don't crash the run on one channel's or one row's failure; isolate and report.
